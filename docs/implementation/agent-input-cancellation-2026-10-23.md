# Pi / Antigravity 通信取消与停止确认（2026-10-23）

接续 ZCode 的通信取消审计。本轮修复 Pi 和 Antigravity 的半帧输入、Pi 未确认控制请求和已占轮次的发送取消，以及 Antigravity 的停止退出确认与无换行超限输出。没有修改手机、服务端或视频管线的生产代码。

## Pi

1. **半帧取消**：stdin 锁内、首次原生写入前建立同步守卫。JSON（含换行）及 flush 全部成功后才解除；写入失败/超时或等待方被取消时，在释放锁前停用连接。原 supervisor 持有 OS 作用域继续清理，不能把下一请求接在半条 JSON 后。
2. **控制请求结果未知**：完整请求发送后，`call` 等待原生响应也有取消守卫。模型/思考配置等请求已发出但调用方不再等待时，原会话进入关闭，不能将未确认的新设置当作旧设置继续使用。收到原生明确响应则解除守卫，保留原错误分类；不是自动重发模型修改。
3. **待发送注册**：`request` 在原生发送前登记的 pending reply，若没有成功移交给响应等待方，则清除该原登记。取消等待输入锁时不会积累无接收者的注册。
4. **轮次已占用但尚未派发**：`prompt` 在 `begin_turn` 后持有独立派发守卫。取消时即使仍在等待 stdin 锁，也关闭原连接并清理原 turn claim，不能永久留下“会话忙碌”。完整 prompt 发出后，既有独立响应任务接管，不因 UI 返回或停止读取事件就中止正常任务。

Pi 一个原生进程对应一个会话。本轮停用的是原会话的进程，不能将这个策略直接用于 ZCode/ACP 这类多会话共享进程的单会话关闭。后续可冷恢复的范围继续由原生恢复能力决定。

## Antigravity

- stdin 写入增加 10 秒期限和锁内半帧守卫。调用取消、失败或超时会关闭原连接；独立 actor 清理原进程组/Job、reader、stderr 和审批桥任务，不依赖取消的调用方。以后续真实退出证明判断完成，不把信号或关管道当作证明。
- 输入通信失败独立记录，活动轮次报告失败，不伪装成正常完成或用户主动停止。如果用户已经明确关闭导致管道失败，仍保留原主动中断语义；先发生的通信失败不会被稍后的关闭覆盖。
- stdout 在读到单条记录 2 MiB + 1 字节时立即停止读取，包括异常输出不写换行的情况。此前 `read_line` 会一直等换行，导致读取阶段没有真正有界。新实现仍以相同的单帧上限拒绝超大记录，非法 UTF-8 也结束原管线。
- **停止现在等待真实清理**。原实现只取走 stdin 即返回成功；忽略 EOF 的原生 CLI 或工具仍可能继续运行。现在 `interrupt` 请求原 actor 关闭，在自然退出宽限后必要时终止原作用域，实际退出及桥任务清理完成后才返回。等待方取消后 actor 继续，重试等待同一原清理结果，不等待被阻塞的 stdin 锁。

这不新增 Agent 工具权限，也不自动批准外部工具。会话结束后能否跨进程恢复仍由既有已验证原生能力控制。

## 验证方式

新增六项回归，均用测试自己创建的私有 Python/shell CLI，先复现旧代码失败再验证修复：

- Pi：2 MiB prompt 写一部分后取消；原生模型修改已读取但响应未回时取消；已占 turn、排队等待另一个阻塞写入时取消。
- Antigravity：2 MiB 半帧写入取消；超过 2 MiB 但不输出换行；忽略 stdin EOF/TERM 时停止不能提前返回成功。

断言同时检查原进程消失、退出回执、不可继续写、pending/turn 清理以及失败/中断事件语义。回归失败也显式回收测试自己创建的进程，不触碰实际 Agent、用户 Core、屏幕、键鼠、剪贴板或模拟器。

macOS 和隔离 Linux：Pi 各 22 项、Antigravity 各 30 项通过，另外各 6 项原有真实/按需用例未启用；两平台 all-targets 严格 Clippy 通过。Windows `x86_64-pc-windows-msvc` 的两驱动 all-targets 交叉检查和严格 Clippy 通过，不代表 Windows 进程 Job 已实机验收。

最终桌面完整库 331 项、Core 92 项通过，另 7 项桌面按需用例未启用；桌面 all-targets 严格 Clippy 通过。没有重复运行未修改的手机/服务端生产代码的全套测试。

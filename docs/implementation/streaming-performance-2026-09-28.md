# 流式更新性能优化（2026-09-28）

## 问题与修改

原先每批事件等待 40ms 后，刷新全局 bootstrap、当前时间线和审批；任务校验又通过 bootstrap 读取所有任务。数据库共用连接锁，这些读取也会与事件写入争用。

- 正文、活动和工具事件直接增量更新前端时间线，按 16ms 窗口合并 React 更新。纯正文无需重新读取全局状态、历史消息或审批。
- 生命周期事件仍读取规范状态，保留结束信息、审批和文件等处理。运行中的思考文本保存在内存，仍按需刷新当前时间线，不读取全局状态和审批。
- 新增原子 `timeline_snapshot`：在同一 SQLite 事务读取时间线及全局事件游标。读取期间缓冲事件，仅重放晚于快照游标的事件；失效请求由前端 epoch 丢弃。断线补齐的事件也进入增量处理，避免漏字或重复追加。
- 任务校验改为按任务 ID 查询，增加事件查询索引；全局快照保留用于初始化、恢复和生命周期同步。
- 灵动岛跳过不影响其状态的正文、活动和工具高频事件。

## 本地测量

同一开发环境、同一 daemon 本地 RPC 路径，优化后各采样 5 次取中位数。开发实例自动重载后无运行中的任务。两次测量间数据有少量变化，因此数字用于观察数量级，不代表固定性能保证。

| 读取 | 优化前中位数 | 优化后中位数 |
| --- | ---: | ---: |
| 全局 bootstrap | 170.9ms | 45.64ms |
| 当前任务 timeline | 148.8ms | 1.69ms |
| 当前任务 pending_approvals（空） | 138.1ms | 0.45ms |
| 新增 timeline_snapshot | — | 1.70ms |

正文事件已绕过这些读取。16ms 是 UI 合并窗口，不是实测帧率；尚未重新测量原生 Agent 首字延迟、事件落库延迟或实际绘制帧率。原生会话初始化、工作区扫描及增长中的 Markdown 解析仍可能影响体验。

可在一次性数据库备份上运行 `cargo run -p agent-store --example streaming_read_benchmark -- /absolute/path/to/backup.db`，复测 Core 读取耗时。该程序打开数据库时会安装索引；结果不含 RPC 传输开销，不应直接与上表混用。

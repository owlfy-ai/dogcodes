# 流式增量批处理与渲染范围优化

此前虽然每 16ms 才更新 React，每个事件仍立即查找时间线、复制数组和记录对象；刷新时还会更新顶层 snapshot 的任务版本号，使侧栏和依赖任务列表的计算反复执行。

## 实现

- `StreamingTimeline.receive` 按序接收并去重，记录最新游标及待处理事件；16ms 窗口结束后，按任务调用一次 `flush`。
- 每批只建立一次记录索引，最多复制一次时间线数组，每个修改行只复制一次。正文片段统一拼接，活动 JSON 每行每批只解析和序列化一次。未修改行保持对象身份。
- 快照读取保存独立事件缓冲，也包含开始读取时尚未 flush 的事件。快照返回后，仅重放晚于其原子游标的事件，清除已经覆盖或重放的待处理队列，避免后续 flush 重复追加。
- 每批只刷新有变化的当前会话；后台会话更新缓存。纯正文不再调用 `setSnapshot` 或更新任务数组。
- 最新任务版本号仍即时记录在 ref 中，取消、审批、重命名和删除在提交操作时读取最新值，不依赖下一次界面刷新。
- 侧栏使用稳定 props 和 memo；普通历史条目与活动行复用未修改对象，跳过重渲染。导航任务 ID 和可用集合也按任务列表身份缓存。

这是轻量拆分：当前会话时间线变化仍会运行 App 和 ConversationContent 的渲染逻辑，尚未改成每条消息独立订阅的状态架构。思考文本的回读路径保持原有行为。

## 测量

新增可复测基准：

```sh
pnpm --filter ./apps/desktop exec vitest bench src/streamingTimeline.bench.ts --run
```

本地样本为 1000 条历史记录、300 条同一正文的增量，每次回放从相同输入开始。旧版正文算法使用逐条 findIndex 和 slice；基线省略事件校验。批处理包含事件校验、索引、更新和拼接。

| 时间线数据处理 | 平均耗时 |
| --- | ---: |
| 原逐事件查找与复制 | 1.5498ms |
| 单次索引批处理 | 0.0851ms |

该样本约快 18.2 倍，只代表这段数据处理代码，不包含模型生成、IPC、事件接收排队、React 或浏览器绘制，不能推导为实际出字速度提高 18 倍。

## 验证

- 相关 8 个测试文件、46 项通过，包括 300 条增量一次 flush、侧栏无新增渲染、后台缓存切换、刷新前取消/审批使用最新版本、快照竞态、重复事件、混合活动语义、逐帧显示和审批流程。
- 全量前端测试 498 项：494 项通过。会话永久删除、草稿项目选择、审查执行结果及额度 HTML 断言这 4 项，与前一次在关闭平滑显示的临时副本中复现的失败一致。
- TypeScript 检查及生产构建通过。未测量原生窗口端到端绘制延迟。

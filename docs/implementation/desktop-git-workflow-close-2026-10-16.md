# Git 工作流共享结束状态

日期：2026-10-16。对应 DT-09/DT-10，延续[后台接续身份](desktop-git-workflow-2026-10-16.md)。

## 行为与持久化

- 新增 `GitClose { taskId, operationId }` / `core_review_git_close`。从组合操作的任一步结束，后台解析到根回执，在原 journal 中原子保存 `closed=true`；保留请求、成功/失败/未知结果及全部子回执。
- 结束是幂等状态变更，重复调用不重新执行 Git。不把“用户已核对并结束跟踪”视为原操作成功，也不把它作为停止正在运行 Git 进程的命令。
- 关闭与接续使用同一 ReviewHost gate 仲裁。关闭先受理时，排队的接续以及直接提交的后续 push 请求都会拒绝；接续先执行时，关闭等待其结果，再禁止后续重试。不取消已发出的外部推送。
- Git 回执查询及后台操作列表派生根工作流的关闭状态；另一个客户端、新服务实例与旧子操作均能看到。单纯历史查询只读，未把结束状态复制成另一套事实源。
- 父链读取校验 task/root、父子身份和请求参数；循环、缺失或超过 256 步明确拒绝，不凭部分链授权接续。长链与重复查询成本仍需后续性能验收。
- 原恢复面板的“完成/结束此次操作”先向后台确认；回复丢失时查询回执，未确认则保留端内待核实记录。另一客户端已关闭时，本端状态查询清除跟踪并停止提供接续；后台仍做最终拒绝。
- 操作详情保留真实结果，另显示“已结束跟踪”，隐藏继续/重试推送。历史详情可发起同一后台关闭操作；网络失败明确提示结束状态尚未核实。
- 当前注册入口为 107 项，其中生产 105 项。通用 receipt 的 closed 字段默认为 false；当前只有 Git 关闭 API 使用它，文件变更结果与执行逻辑未改变。

## 后续推进：推送目标绑定

以下是当时确定的要求；后续实现及专项验证见[推送目标记录](desktop-git-push-target-2026-10-16.md)。

共享结束状态不解决仓库在两次操作之间被修改的问题。下一工作块需在后台记录并核实本次提交对应的仓库、分支、commit OID、上游引用和推送地址，接续使用明确源 OID/目标引用；不能仅检查后立即执行依赖当前 HEAD 的默认 push。Git 的 refspec 可指定源提交及目标引用，参见 [git-push](https://git-scm.com/docs/git-push)。

提交成功后无法核实目标，应保留“提交成功”的事实并要求核实推送范围，不能把它误报提交失败，也不能重做提交。提交 hooks 或其他客户端可能继续移动 HEAD，需要能识别本次实际提交，而非事后简单读取最新 HEAD。可评估 [GIT_REFLOG_ACTION](https://git-scm.com/docs/git#Documentation/git.txt-GITREFLOGACTION) 与有界 reflog 查询，但必须覆盖 reflog 关闭/清理、hook 继承环境、多个匹配和服务崩溃；尚未把该方案作为已实现能力。

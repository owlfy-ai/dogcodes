# 项目运行分析：异常收尾与原生会话清理（2026-10-22）

## 范围

桌面和手机共用的项目“运行”配置分析：读取项目证据，通过独立 Agent 会话提取命令；分析不启动项目命令。沿用原 operationId、请求指纹、目录/配置 generation 和运行回执协议。

## 落盘失败

分析完成先克隆最后成功保存的 catalog，在候选副本上更新命令及回执。只有原子保存成功，才向共享缓存和订阅发布候选结果。

保存失败立即停止当前批次的后续 Agent 调用。保留最后成功保存的命令，将所有未完成目录和当前运行回执终止，排入该项目的待保存收尾；不会把未保存的新命令留在可启动的缓存里。故障期间读配置/回执和启动检查返回可重试的存储错误。磁盘修复后，读取自动保存原批次的失败状态再返回，不重新调用 Agent；其它项目已有的有效缓存不受此项目的保存失败影响。

读取和新编辑/新分析提交均在同一缓存锁内检查待收尾状态；对 generation 再核实后才保存，防止旧收尾覆盖新配置。rename 后目录 fsync 的不确定错误仍使写入停用，不能在未知提交结果上继续覆盖；重启后从实际文件恢复。

## 中断与重启

分析任务由带 generation 的服务生命周期守卫持有。队列关闭、任务取消、panic 或旧批次被新分析替换时，守卫只收尾自己的 generation；未完成目录变成错误、对应分析回执变成 interrupted，原命令保留，不修改新批次。正常完成后的守卫不再写文件。

从磁盘读取重启前的 analyzing/running 状态时，先原子保存 interrupted 状态才发布恢复结果。无法保存则保留原文件并报告错误，不只在内存里假装恢复成功。同一个 operationId 的查询/重放仍返回原批次，不自动重新执行分析。

## 原生 Agent 会话生命周期

- 启动阶段由独立任务持有临时目录及服务退出保护。调用方中途取消后，晚到的原会话仍进入清理，不会继续发送分析 prompt。
- 获得 handle 后，原会话的 interrupt/shutdown 与等待结果的调用方解耦。分析被取消、panic 或等待 shutdown 时被取消，均不取消清理任务。
- 正常成功仅 shutdown；错误/取消先 interrupt。只访问原 driver/handle，不误关后来的连接。
- 关闭失败、超时或 panic 时，原分析标记为中断并停止剩余目录；后台保留原临时目录、driver、handle 及退出保护，按 1/2/4/8/16/30 秒退避重试关闭。该项目暂拒绝新分析，原回执仍可读取，不妨碍其它项目。
- 原 driver 确认关闭后释放退出保护及临时目录，才允许该项目再次分析。外层关闭等待改为 15 秒，避免提前截断 Claude 内部最长八秒的关闭等待。

这里的确认依据是 AgentDriver.shutdown 的结果，不是对任意外部 PID 的推断。整体 Core 被强制结束、每个原生驱动启动超时/崩溃后的系统级子进程清理，仍须另行审计和平台验收。

## Codex 关闭确认

发现 CodexDriver 在等待关闭前先从会话表删除 actor：等待被取消或超时后，重试会把“会话表为空”当作已关闭。现保留原 sender，收到原 actor 的关闭确认或确认该 actor 已结束后才移除；用 same_channel 防止迟到确认删除同 ID 的替换连接。重试只关闭原会话，不发送任务。

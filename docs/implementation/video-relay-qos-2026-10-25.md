# 二进制视频 ACK、延迟基线与拥塞恢复

日期：2026-10-25。继续 [RustDesk 对照](rustdesk-video-reference-2026-10-25.md) 的网络反馈项；当前是代码与隔离验证，不是实际地区/弱网验收。

## 已复现的问题

四个新增回归在修改生产实现前均失败，见 `/tmp/dogcodes-relay-qos-before.log`：

1. 最近 40 个样本直接取最小值，旧最小值淘汰时会把持续增长的队列学成正常延迟；连续增长的队列反而得到更高码率。
2. 降速之后的一次集中 ACK 可立即累满“干净十次”，没有恢复观察期。
3. 无 ACK 的减速只在 `push` 新帧时检查，静止之后没有新画面就不再触发。
4. 超时等待被作为延迟样本；若第一张图一直没有 ACK，这个等待时间反而成为基线，首次超时不会减速。

## 实现与依据

参考本机 RustDesk `src/server/video_qos.rs` 对新鲜回复、超时制动、迟到回复、路径基线与排队增量的区分；本项目独立实现 `video/qos.rs`。参数和协议按本项目重设计，没有复制另一产品的控制器。

- 每条二进制视频路径只保存 32 个新鲜 ACK 延迟。更低值立即生效；旧最小值只能在前后两段的较低延迟不再明显上升时逐渐抬高，最多每秒 25ms。持续上升的队列不能快速自我消除为新基线。
- 连续三次超过基线 150ms 才减四分之一；超过一秒时减半。两次降速至少相隔 500ms，维持原有最小/最大码率边界。
- 增加码率要求至少十个干净回复、连续观察一秒，距上次降低及增加也至少一秒；每次增幅仍为 8%。一个瞬时 ACK burst 不等于网络已经稳定恢复。
- 原 owner 的 100ms 控制循环读取 `target_bitrate` 时主动检查无 ACK，`push` 也做相同检查。最老未确认画面超过两秒后，每秒最多减半一次；没有 inflight 的正常静止不会减速。
- 超时不会加入基线样本。保存该次超时之前的发送时间边界，旧画面的迟到 ACK 只释放累计窗口，不二次降速、不学习基线、不累加恢复次数。首次过期 ACK 也不凭空创建路径基线。
- 部分迟到 ACK 不清掉尚未结束的超时制动时钟，避免在一秒内提前再次制动；窗口清空后可结束本次等待。重绑仍重建 QoS，旧视频代次 ACK 的边界保持。

本轮改动作用于 `RelayVideo` 二进制视频 ACK 调速。RTP 路径继续使用 WebRTC 的拥塞估计，未把两套反馈直接叠加。没有更改手机/服务端生产协议或加入用户可见的操作记录。

## 可重跑的简化链路模型

新增 `scripts/relay_qos_trace.rs`，直接使用当前 QoS 模块，以八项在途窗口、20fps、目标的 90% 载荷和固定 80ms 传播时间模拟 FIFO 链路，容量按 1.5M → 300k（4–14s）→ 1.5M bit/s 切换。不访问网络或显示器：

```sh
rustc --edition=2024 -D warnings scripts/relay_qos_trace.rs -o /tmp/dogcodes-qos-trace
/tmp/dogcodes-qos-trace
```

该模型中 4s 的目标约 1.89M，6s 已降到约 354k；14s 容量恢复时目标约 293k，36s 才回到约 1.60M，后续约 1.1–1.9M 之间呈锯齿。结果保留于 `/tmp/dogcodes-relay-qos-trace.log`，明确说明恢复速度和波动仍需调校，不能宣称弱网优化已经全部完成。模型不含真实 H.264/IDR 峰值、重传、分片、decoder、换路和完整 RelayVideo 准入，不能代替真实吞吐/体验测试，也没有把这些样本值设为验收标准。

## 接下来仍要处理

发送窗口满时，当前丢帧信号仍可能让生产者重复请求 IDR，需要把窗口余量/消费反馈传回编码调度端，并保持跨 Output/换路/代次的请求归属。已检查手机 `RelayVideoReceiver`：解码失败或主动丢弃也推进累计 ACK，不能改成等待“成功解码全部旧帧”才允许恢复，否则可能锁死满窗。随后需量化限速、抖动、断网、重连、控制/附件争用与实际 decoder 消费，并评估恢复速度/震荡；本轮的合成时钟回归不能证明这些场景已完成。

动态最终几何、Linux 硬编、Windows 原生采集/零拷贝、GPU 挂起/设备恢复、硬件文字质量及平台/手机真机继续；原 PC 功能对齐、操作恢复、metadata/辅助事务、Core 强退与跨物理代次、推送与官方部署全部保留。没有切换日常 Core、调用真实模型、启动模拟器或操作用户屏幕/键鼠/剪贴板，原有三个 Docker dev 服务保留。

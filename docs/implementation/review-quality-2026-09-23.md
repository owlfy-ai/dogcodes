# 审查质量升级：结构化问题与历史定位（2026-09-23）

## 已确认的产品范围

只保留代码审查、安全检查、性能分析。逐轮入口和项目 Diff（Git 比较及目录会话比较）入口共用执行与结果处理。复用已有多 Agent、额度下拉和图标，不增加模型服务或 OCR CLI 依赖，不恢复检查测试、对照要求、评估影响。测试文件仍是代码审查的合法输入。

按此前讨论的顺序实施：先结构化问题和历史 Diff 定位，再规则匹配与文件覆盖，后续才是分组、同版本上下文检索和独立 AI 复核。本次交付前两项的基础能力。

## 借鉴来源与取舍

阅读本地 `~/Workspace/study/open-code-review`，版本 `0243a38`。借鉴以下设计，用本项目 Rust/React 和原有 Agent 协议实现，没有执行 OCR 或另建模型接入：

- `internal/model/review.go`、`internal/tool/code_comment.go`：将问题拆成严重程度、文件、行号、代码片段、原因和建议，程序检查结构。
- `internal/tool/comment_collector.go`：集中收集问题并去重。本次仅合并同文件、侧别、位置、标题、描述和证据一致的重复项，保留最高严重程度，不做可能误删独立问题的语义去重。
- `internal/config/rules/rule_docs/`：规则按文件特征匹配。本次内置三类检查重点，以及 Rust、JS/TS/React、Go、Python、SQL、权限/存储目录、测试文件的简洁检查清单，不照搬风格限制与默认测试排除。
- README 的确定性工程与 Agent 分工、`internal/agent/grouping.go` 以及结果过滤提示词：将定位校验与模型判断区分。缺少证据不能简单删除可能重要的问题；本次保留为待核实，不把位置核对称为缺陷确认。

## 执行与结果

`review_analysis` 从已冻结、脱敏的 packet 生成确定性 file ID、目录身份、前后行数和每文件规则清单。模型仍在一个独立 Session/Run 中分析原材料，不调用工具、不访问当前项目。要求返回版本化 JSON、实际检查过的 file ID 和问题列表。

`ReviewRun.report` 是可选字段；旧事件无需迁移，原始 `result` 保留。结构有效的问题按 critical/high/medium/low 排序；逐项校验失败会明确告知，并提供原始回复。普通文字、非法 JSON、缺少必需字段和不支持的协议版本均退回原文展示，标明覆盖和位置未确认。不会自动再请求模型来修复格式，避免额外消耗与静默重跑。

定位仅检查引用侧保存的代码：1 起始行号、连续原文（最多 80 行）必须匹配；行号错误但片段在该文件该侧唯一出现时可纠正。未知文件、缺失原文、重复片段或不匹配均保留为待核实，禁止直接定位。该校验不证明业务逻辑或安全/性能推断成立。

每文件覆盖为 Agent 报告已检查、未报告检查、部分原文缺失、原文不可用。UI 明示这是 Agent 自报，程序只核对清单与材料可用性，不能证明模型真实分析了每行。空问题列表不会自动宣称全部通过。未确认覆盖及其他警告随来源一起进入主任务后续上下文。

## 历史 Diff 定位

`review_source(taskId, runId, fileId)` 从该任务 `review.started` 的持久化 packet 读取文件前后原文，并核对输入 SHA-256。桌面命令校验窗口所属任务；守护进程提供同样的 Core 查询。不同目录同名文件有不同 file ID 和 root ID，界面显示可读路径，不显示内部目录 ID。

点击已核对问题后，两个入口都用 `ReviewFindingDiff` 打开只读送审版本，复用 `ReviewText` 的差异渲染、语法着色和行号。定位行自动展开、滚动和标亮；关闭后返回触发按钮。项目刷新、比较缓存过期、重启或重试不改变这份持久化来源。读取或校验失败只显示错误，不回退当前文件。

前端比较有 100ms、5,000 编辑步和 20,000 总行数预算。大文件、超时或一侧原文缺失时，明确提示只展示定位附近保存的代码片段，不能冒充完整 Diff。显示的是脱敏后实际送审版本。

# Markdown 流式渲染与任务启动分段计时

## Markdown

`StreamingMarkdown` 使用与正文一致的 remark/GFM/math 解析器识别顶层块。已经稳定的块保留独立的 memoized React 子树与上下文，新增文本只解析末尾区域。保留最后两个顶层块用于重新解析，防止尚未完整输入的列表标记等内容改变前一个块的边界。

末尾未闭合的顶层代码围栏先显示源码，闭合后进行语法高亮。完成回复时使用完整文档解析，内容修正时重置缓存。定义式链接和脚注需要跨块解析，检测到定义后回退全文解析，保持语义一致。单个超长列表、段落或代码块仍需要解析其增长中的内容；本次未引入字符播放动画或额外输出延迟。

逐字输入对照测试覆盖标题、列表、引用、表格、代码、公式、延迟出现的链接定义、脚注与 HTML，验证增量分块与完整解析结果一致；DOM 测试验证稳定代码块保留，未闭合代码块延后高亮。

可复测基准：

```sh
pnpm --filter ./apps/desktop exec vitest bench src/MarkdownStreaming.bench.tsx --run
```

本机 jsdom 下，60 组标题/段落/代码块，包含初始挂载及 40 次末尾追加，3 次样本均值：

| 路径 | 总耗时 |
| --- | ---: |
| 整条消息解析及高亮 | 772.51ms |
| 稳定块缓存及末尾增量处理 | 311.91ms |

约 2.48 倍提速。对照是原先的整条 `react-markdown` 解析及高亮路径，不包含全部定制控件；优化路径使用实际 `MarkdownMessage`。这是本地合成 CPU/DOM 基准，不是桌面 WebView 绘制帧率或模型输出速度。

## 启动诊断

Core 通过可选诊断 sink 记录单调时钟耗时，覆盖：命令校验与写入、调度、工作区锁与范围查询、工作区快照捕获及 checkpoint、Review 基线、辅助上下文、历史桥接、会话上下文、原生会话创建/恢复、会话身份持久化、操作捕获、提示词提交及记账、首个驱动事件、首段正文、首段正文发布。

正文识别同时支持 `TextDelta` 和 ACP 的 `Presentation(type=message)`，不将思考文本误算为正文。首段只计一次；失败或提前返回时也关闭正在计时的阶段。阶段的 `end` 表示范围退出，不等于成功，需结合 `run_failed` 或正常结束标记。`run_stream_finished` 只表示流消费完成，原生 Agent 自己的失败仍以规范事件为准。

桌面服务异步写入数据目录中的 `turn-startup-timing.jsonl`。日志仅含时间、任务/run/trace ID 和固定阶段名，无提示词、正文、文件内容或凭据；有界队列满时丢弃诊断记录，不阻塞执行，超过 2MiB 轮转并保留一份旧日志。它不进入任务事件流，不触发 UI 刷新。

```sh
python3 scripts/summarize-turn-startup.py \
  "$HOME/Library/Application Support/dev.dogcodes.desktop/turn-startup-timing.jsonl" --last 5
```

计时起点为 Core 收到 SubmitTurn，结束于 Core 收到正文及落库发布。前端创建对话、IPC 往返、WebView commit/paint 不在这个总时长内。`accepted_to_first_text` 包含原生驱动、服务端和模型等待，不能直接解释成纯网络或纯模型推理时间。

## 真实只读测试

在现有 DrillHUD 项目以 Cursor 发起简短测试，要求只回复测试文字，不读取或改动文件、不执行工具。测试对话已归档。这是少量样本，不代表所有 Agent 的分布。

| 阶段 | 新对话 | 同一对话后续轮次 |
| --- | ---: | ---: |
| Review 基线准备 | 14,106ms | 28.59ms |
| 原生会话创建/恢复 | 2,929ms | 2,988.70ms |
| 辅助上下文 | 102.85ms | 773.85ms |
| 提交后到首个驱动事件 | 1,983.30ms | 2,117.00ms |
| 提交后到首段正文 | 未记录 | 3,769.16ms |
| 首段正文落库并发布 | 未记录 | 1.76ms |
| Core 收到提交至首段正文发布 | 未记录 | 8,008.84ms |

首次测试暴露了 ACP 正文通过 Presentation 交付的计时遗漏；已修正并以单元测试覆盖，后续成功样本验证了正文及发布两个标记。开发服务重载后曾有一轮在驱动准备完成前失败，不计入成功样本。

DrillHUD 没有 `.git`；新对话需要建立非 Git Review 基线。此次计时表明基线准备是新对话的明显耗时点，复用后仅需约 29ms。本次保留执行前建立基线的时序，尚未改变其扫描或存储实现。后续轮次仍有约 3 秒原生会话准备和 3.77 秒正文等待，这些不属于 Markdown 渲染开销。

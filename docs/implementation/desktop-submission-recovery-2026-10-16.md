# 普通发送与新建会话的分阶段恢复

日期：2026-10-16。对应 DT-09，复用[原身份与作废接口](desktop-submission-identity-2026-10-16.md)。App 的实际普通发送入口已接入；本工作块没有变更数据库、原生协议、签名或公证配置，不代表所有 DT-09 入口已通过验收。

## 执行与恢复

`submissionOperations.ts` 在任何创建会话、确认上下文或提交消息之前，持久保存本次原意图：正文、目标 Agent、模型、思考强度、权限模式、已准备的附件引用、原任务版本及各阶段独立的固定操作 ID。新建会话预先分配 taskId；普通未发送草稿仍留在本端。

每个意图使用独立 localStorage 键，按原 scope 协调本机并发；同一现有任务有待核实意图时拒绝新发送，不覆盖旧记录。用户显式新建的不同草稿有不同 scope，可以分别跟踪。损坏或无法写入的存储阻止后续业务变更，不自动丢弃记录。存储只用于恢复原请求，后台回执和任务版本仍是受理事实源。

创建阶段核对原回执指向的 `task.created` 事件，包括 taskId、项目、标题、目标 Agent、causationId 和版本 1。切换 Agent 时保存原上下文区间、包哈希、源版本和确认 ID；通过原回执最后的 `task.preferred_executor_changed` 事件核对目标及下一阶段版本。最终提交快照必须写入成功才调用 SubmitTurn。

恢复先查原最终回执，再检查当前任务是否存在、空闲且项目/目标/版本与原边界一致。会话已变化时不换用新版本重发。即便本地 checkpoint 尚未写入，也可以从原创建/上下文事件推导同一最终命令，查询其他窗口已提交的结果。受理后以原 `turn.queued` 的命令关联、任务和序列核实消息身份；受理表示进入执行流程，不表示 Agent 已完成。

`SubmissionRecovery.tsx` 提供“核实发送结果”“继续原发送”“放弃原发送”。挂载只展示持久记录；查询和继续由用户明确操作，重开界面不自动重新创建/切换/提交。正常首次发送期间不显示未知结果警告。可展开查看原正文、附件名和发送选项；原 Agent 不可用或禁用时可核实、放弃，但不能继续执行。

放弃不能仅删除本地记录：未受理的创建/上下文先调用后台作废；若该阶段已受理（包括与作废竞争时刚被受理），还须核实或作废其确定边界上的原最终 SubmitTurn。消息若已受理则报告原受理，不能声称已取消；已创建空会话和已确认的 Agent 切换保持原结果。作废失败或回执事件暂时不可读时保留记录。

## 界面与输入保护

App 不再把所有失败都当作未发送并把旧正文塞回输入框。只有原意图尚未保存的准备失败、且会话及草稿修订均未变化时恢复输入；已有持久意图由恢复面板持有，避免将结果未知的原消息作为新消息重发。

附件使用本次捕获的 ID 清理，后来选择的附件不受迟到结果影响。消息乐观占位通过原 commandId/规范 sequence 对齐历史，不再凭相同正文匹配。订阅先到达受理事件时同样使用 causationId；另一窗口提交相同内容不会错误消除本次占位。新会话创建后的自动跳转也检查原输入上下文，用户已切到别处或输入新草稿时不会拉回旧会话。

浏览器 Demo 补充固定创建/上下文/发送身份、精确输入绑定的内存回执、作废及关联事件；它不提供生产级持久化。模型切换测试使用绑定原输入和版本的回执/事件夹具，避免无条件成功 mock 掩盖新恢复流程。

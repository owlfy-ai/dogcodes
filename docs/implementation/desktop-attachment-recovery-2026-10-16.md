# 附件上传回执与原内容校验

日期：2026-10-16。对应 DT-08/09；继[普通发送恢复](desktop-submission-recovery-2026-10-16.md)后，补齐其附件准备阶段。当前实现不包含自动删除历史附件，不改变数据库及发布凭据配置。

## 后台拥有文件与上传结果

附件保存、回执查询和读取移至 `attachment_service::AttachmentStore`，由 daemon `ServiceControl` 持有。Tauri 的 `core_save_attachment` / `core_read_attachment` 只转发业务调用；下载保存窗口仍属于本机适配。新增 `core_attachment_upload_receipt`。普通服务连接断开不取消已经受理的文件写入，查询和重发都使用原上传 ID。

`AttachmentUploadRequest` 明确包含 uploadId、原文件名、MIME、字节数和 SHA-256。uploadId 为规范 UUID，同一身份不能绑定其他文件名、类型、大小或内容。RPC 用 base64 传递二进制，避免把 25 MB 文件展开为 JSON 整数数组后超出既有 64 MB 帧上限；读回也采用后台 base64、Tauri 转回字节的方式。大小和编码均在后台检查。

后台在应用数据目录的 `attachments/uploads/<uploadId>/` 保存原请求清单和内容。内容文件名由固定 `payload` 加安全扩展名生成，原文件名只作为元数据，避免路径穿越和 Windows 保留文件名问题。先在私有临时目录完整写入并同步，再发布目录；异常路径回收本次临时目录。成功回执只有完整原文件存在且大小/摘要匹配时才返回。并发发布或回复丢失查询同一对象，不覆盖已有对象来消除冲突。

回执只读：不存在返回 null，不创建目录；发现已存在但损坏、缺失或不匹配的对象报错，不能把它当作未上传而覆写。服务重开后直接从清单和原文件核实。读取只允许应用附件目录，托管附件必须匹配其清单；旧 UUID 目录里的历史附件仍可读，清单和临时文件不作为附件暴露。

## 内容绑定与发送

`PromptAttachment` 新增可选 integrity（SHA-256、byteLength）。旧记录反序列化为 None，序列化继续省略字段，不改变旧命令指纹。新上传返回完整 integrity，发送意图和 CoreCommand 指纹保留该信息。

Core 在命令受理时校验原文件，并在会话/上下文准备完、真正调用 driver.prompt 前再次校验。文件变动时不交给驱动，原轮次记录失败；命令已受理不等于消息已经交给供应商。图片内联编码使用本次实际读取的字节再次核对摘要，不能在校验后重新读取不同内容而编码。批量大小限制使用原字节数并检查溢出。

非图片仍按现有供应商协议传递文件路径；检查不能保证同一操作系统用户随后主动修改文件后，外部 Agent 更晚的路径读取仍获得旧字节。没有将此实现宣称为外部文件系统的不可变快照。旧的无摘要历史引用继续保留原兼容语义，新托管上传提供原内容校验。

## 窗口重开后的附件恢复

前端在第一次上传 RPC 前保存原请求元数据，使用当前附件的固定 UUID。失败或超时先查询原上传，查询本身失败时不盲目重传。原 File 仍在时可以复用相同身份和字节重试；记录不保存 base64 或浏览器 File。

记录保留到完整发送意图已经持久化才移交并移除，覆盖“附件已上传，但还没建立发送意图就关窗”的空隙。重开可显式核实原导入，并将已确认文件加入当前草稿，不需要原浏览器 File；准备发送时再次核实回执。没有查询到完整上传时要求重新选择文件，不自动上传或发送消息。正常正在发送期间、或附件已经在当前草稿中时，不重复显示恢复警告。

“隐藏导入记录”只清理本机元数据，不删除后台文件或历史引用。附件选择、未发送草稿依旧各端独立；实际文件和回执已由后台持有。持久元数据位于应用存储，不写入源码仓库。

## 验证

前端累计 66 个不同用例最终通过：上传状态机 8、导入恢复界面 3、附件展示/消费 9、发送状态机 15、会话发送界面 21、命令客户端 10。最终桌面类型检查通过；首轮发现一个测试仍把恢复附件视为必有 File，修正可选字段访问后通过。

原生专项共 **16 项通过**，按同一顺序链执行并最终收取 exit 0：

- `cargo test -p desktop --lib attachment_`：10 项，覆盖服务重开和只读查询、原输入绑定、字节错配、损坏/缺失文件不覆写、路径与符号链接边界、旧附件读取、并发发布，以及 loopback RPC 回复丢失后的另一客户端核实。
- `cargo test -p agent-store --test attachment_integrity`：4 项，覆盖摘要进入回执身份和历史、受理前内容变化不排队、会话准备时变化不交给驱动且记录失败，以及旧引用的序列化兼容。
- `cargo test -p driver-api --lib attachments::tests`：2 项，覆盖图片/文件原传输语义，以及编码时原摘要检查。

首个原生进程曾等待编辑器已有 Cargo 检查释放锁，之后同一句柄完成；没有结束其他进程或因为等待而另起重复编译。前端日志 `/tmp/dogcodes-attachment-{frontend,client-final,types-final}.log`；原生日志 `/tmp/dogcodes-attachment-{service-native,integrity-native,driver-native}.log`。格式/变更空白检查通过，没有运行全套测试、打包或真实 Agent。当前注册清单为 116 项 handler（114 项生产入口）。

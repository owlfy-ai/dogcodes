# 二进制视频恢复速度与拥塞试探

日期：2026-10-25。接续 [ACK/延迟基线](video-relay-qos-2026-10-25.md) 和 [编码前准入](video-output-admission-2026-10-25.md)。本轮只修改 PC 二进制视频 ACK 控制器和验证入口；RTP 继续使用 WebRTC GCC，手机和服务端生产代码、协议不变。

## RustDesk 参考与独立实现

继续核对本机 RustDesk HEAD `53996e3c4` 的 `src/server/video_qos.rs`，重点参考 `limit_fps_change`、`recover`、`on_reduction` 对新鲜样本、恢复前水平和恢复失败的保护。采用这些控制思路，独立设计本项目的码率策略，没有复制 RustDesk 的代码或协议，也没有把其 FPS 控制参数直接套入码率。

旧控制器在低延迟时每秒增加 8%，带宽恢复后提速较慢；同时把低于 150ms 的排队增量都当成可以升速的信号，稳定链路也会反复较深地降速。单纯把增幅提高到 25% 虽然恢复更快，却加大稳定链路波动；该试验没有保留为最终策略。

最终实现位于 `apps/desktop/src-tauri/src/daemon/remote/video/qos.rs`：

- 增加要求至少十个新鲜 ACK、持续一秒，而且 ACK 对应的帧须在最近一次增加或降低目标之后发送。此前已排队的回复不能证明新目标稳定。
- 连续观察窗口保存最大排队增量。只有整个窗口均低于 25ms，才记住该次稳定目标；最后一个回复突然变快不能把整个窗口算作低排队。
- 低于已经观察稳定的目标时，可按 25% 恢复，但不越过该稳定目标，也不越过最近失败水平的九成。接近失败水平或探测新容量时，每步只增加 5%；只有重新跨过失败水平并取得新的低排队观察，才解除该保护。历史目标只是恢复线索，不代表测得了真实可用带宽，实际载荷仍须后续检验。
- 排队增量 50–99ms 保持目标，不继续增加；连续三次达到 100ms 才减速。100–299ms 减 10%，300ms 起减 25%，额外一秒起减半，仍受 500ms 降速间隔保护。
- 正常降速前帧的回复仍能证明拥塞正在恶化，避免带宽骤降时只能等待新帧才降速。只有已触发超时处罚的旧帧，继续按原规则排除，既不重复处罚也不贡献恢复样本。曾试验把所有降速前旧帧都排除，但它使骤降响应变慢，最终未采用。
- 路径基线仍每秒最多上调 25ms，但两半样本最低值的上升容差由 20ms 收紧到 5ms，避免较慢增长的队列也被学成正常路径。

## 可重跑模型与前后对照

`scripts/relay_qos_trace.rs` 直接引用生产控制器。虚拟步长 10ms、在途最多八帧，默认 20fps、目标码率的 90% 载荷；FIFO 服务后再加传播延迟，按最新已释放帧产生累计 ACK，与 `RelayVideo::ack` 的采样方式一致。包含恢复、永久降速、容量增加、500ms 路径、孤立抖动及 200ms 批量确认；额外检查 10/50fps、60%/100% 编码载荷和 0.5/4Mbps 容量的八个组合。

```sh
rustc --edition=2024 -D warnings scripts/relay_qos_trace.rs -o /tmp/dogcodes-qos-trace
/tmp/dogcodes-qos-trace
rustc --edition=2024 -D warnings --test scripts/relay_qos_trace.rs -o /tmp/dogcodes-qos-tests
/tmp/dogcodes-qos-tests
```

相同模型、分别加载修改前备份和最终生产控制器的结果：

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 1.5M→300k→1.5M，恢复后达到原目标九成 | 19.5 秒 | 11.3 秒 |
| 恢复后达到原目标全部 | 21.5 秒 | 11.3 秒 |
| 骤降两秒后的目标 | 约 354kbps | 约 325kbps |
| 稳定 1.5Mbps 链路，末 20 秒目标范围 | 1.09–2.02Mbps | 1.44–1.78Mbps |
| 同一稳定链路，末 20 秒实际通过的载荷 | 1.32Mbps | 1.46Mbps |
| 同一稳定链路，按时间采样的 ACK 延迟 P95 | 300ms | 250ms |

这些是模型结果，不能当作真实网络、手机解码或主观体验的验收。并非所有指标都改善：永久降到 300kbps 的模型中，末段载荷由约 266k 增至 286kbps，但采样延迟 P95 从 300ms 增至 360ms。低带宽恢复后的排队、抖动与吞吐折中仍需调校，没有把提速等同于所有弱网问题都已解决。

对未知更高容量的试探也从原来的 8% 改为更保守的 5%，需要更多观察；回到已观察目标的恢复速度，不能代表发现未知更高带宽的速度。后续须同时衡量队列、吞吐、恢复和新容量发现，不能只优化这一个恢复样本。

模型没有 H.264/IDR 峰值、重传、真实分片、完整 RelayVideo 字节准入、decoder、换路和业务/附件争用，也不模拟实际 GCC。真实端到端体验仍应在 P2P、TURN 和 WSS 上分别验证。

## 验证与边界

- 八条控制器回归与五条模型回归共 13 项通过，Linux CI 已接入独立 `rustc --test` 入口。旧控制器在“恢复不超过十二秒”和“稳定链路不出现深度锯齿”两条模型回归上失败。

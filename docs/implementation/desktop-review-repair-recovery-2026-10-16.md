# 开始修复：原意图与分阶段恢复

日期：2026-10-16。对应 DT-09；复用[命令只读回执](desktop-command-receipt-2026-10-16.md)，保留“开始修复”中性按钮文字，仍交给主对话 Agent 执行。

## 原问题

`ReviewRepairControls` 原来仅通过组件 ref 保存操作 ID，重开报告丢失；重试又读取最新 task.streamVersion。用户在编写框选择不同主 Agent 时，还会先自动确认上下文，再提交修复。若任一步回包丢失，不能据当前 Agent 或新的版本判断原修复是否已受理，也不能换 ID 再次切换/提交。

## 当前行为

- `reviewRepairOperations` 在任何变更前持久保存原报告 ID、输入哈希、排序后的问题索引、主 Agent、原任务版本、上下文请求/包哈希/独立命令 ID，以及最终提交的独立命令 ID。存储失败则不发送变更。上下文预览是只读准备工作，允许在保存前完成。
- 不需要切换 Agent 时，直接冻结原任务版本。需要切换时，先保存完整上下文步骤，再查询/确认这一原请求；确认成功或查询到原回执后，按回执 lastSequence 读取原事件，核实事件的任务、类型、causationId、目标 Agent 及实际 streamVersion。当前会话必须仍停留在该版本、空闲且使用原目标 Agent，才保存最终提交版本并继续。不会硬编码“版本加二”，不会使用后来变化的版本重新提交。
- 最终提交前查询原修复回执；回包丢失也先查询。已受理则结束跟踪，不重新发送，不要求当前会话仍空闲或仍使用原 Agent。未确认时保留原阶段和全部参数。上下文已受理不等于修复已提交，修复已受理不等于任务完成。
- `ReviewRepairRecovery` 在重开报告后显示原问题和主 Agent，提供“核实修复结果”“继续原修复”和显式结束跟踪。挂载只恢复界面，不自动切换 Agent 或发送任务。待核实期间禁止新建覆盖同一报告的修复意图，改变当前勾选或编写框 Agent 不会替换保存的请求。
- 结束跟踪不取消后台任务或撤销已确认上下文，并提示用户再次发起前核对重复任务。迟到回包只清理匹配操作 ID 的记录；报告切换后再返回、另一项待核实记录替换原记录时，旧 UI 回调不清空新的选择。
- 同一 JS 环境的面板/重复点击按报告串行；支持 Web Locks 的同源窗口还按同一作用域协调。后台命令幂等仍是受理依据。这不是跨设备的全局修复工作流：不支持 Web Locks 的不同窗口并发准备、手机无本地意图缓存时的工作流发现仍需后续专项评估，不能以浏览器锁冒充服务端仲裁。

后台受理事实继续存入已有事件/回执。客户端记录只保存恢复所需意图，不保存审查全文或新增凭据。不改变数据库结构及用户数据，不涉及签名配置、服务部署或手机实现。

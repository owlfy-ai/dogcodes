# 安全检查：专项规则、证据链与复核（2026-09-26）

## 范围与架构

逐轮和项目 Diff 的安全检查继续调用用户选定的第三方 Agent，复用现有接入、额度、独立会话、取消和冻结检索。dogcodes 不新增 LLM 客户端或模型服务，不安装外部 skill。代码审查和性能分析仍使用原有输出契约。

本轮借鉴 Cloudflare [security-audit-skill](https://github.com/cloudflare/security-audit-skill) 的证据要求、反证复核和显式覆盖思想，编写适用于当前静态变更审查的中文规则与宿主校验。没有照搬其全仓库审计编排或动态验证执行流程。

## 已实现

- 六类专项：身份与权限、输入与危险操作、敏感数据与隔离、Agent 工具与审批、桌面与本地通信、安装与更新。要求依据代码判断适用性；提示注入文本、危险 API 名称、同权限用户可读配置或普通更新失败本身不构成漏洞证据。
- 每个候选问题增加 `security`：攻击者与已有能力、信任边界、触发条件、现有防护、潜在影响、入口/传播/危险操作引用链、未解条件和后续验证方案。
- 宿主检查链条角色顺序、2–8 项上限、与问题同项目同版本且锚定变更文件、冻结行号与原文。引用可来自已冻结的关联文件；模型提供的展示路径由宿主重新解析。格式或引用不合格保留原问题并标明缺失，不静默删除候选问题。
- `evidenceStatus=source_checked` 只表示字段和引用通过检查，不证明路径语义或可利用性。`runtimeValidation=not_run` 固定由宿主设置，不接受 Agent 自称执行成功。
- 独立会话复核增加边界分析、防护反证、影响分析与未解条件。初审证据不完整、仍有 blocker、独立分析缺失或仍有未知条件时，`confirmed` 降级 `uncertain`；原问题和 Agent 理由保留。有依据的反驳仍保留为 `refuted`。复核可返回完整 `securityEvidence` 补齐初审证据，宿主用相同规则重新校验并单独保存，不覆盖初审。
- 完整复核可以得出待核实结论，不因条件未知而显示执行失败；缺少必填复核分析或返回协议不完整才标记未完成。未执行复现是静态审查的统一边界，blocker/unresolved 用于具体缺失的权限、可达性、部署等事实。
- 每文件固定记录六类检查的 `reviewed`、`not_applicable`、`needs_context`、`not_reported`。前两项必须附理由和可核对的本文件引用；重复记录、跨项目引用、超限或无依据均不计完成。缺少专项记录时即使 findings 为空，也不能将该组判为完成。
- 分组报告合并重新计算专项缺口，避免初始化或组外文件的缺口警告残留。原材料重试及投影重建保留专项记录。
- 结果界面显示专项缺口、潜在风险、证据链、待验证条件、独立安全复核依据与“未执行漏洞复现”。旧报告缺少这些可选字段时明确显示未记录，不补造历史证据。
- 选择问题交回主 Agent 修复时，保留安全证据、未解条件和复核分析；正常来源回流也携带验证程度及 blocker 摘要。

## 契约与边界

保留审查协议版本 1，以可选持久化字段扩展 `CheckedFinding.security`、`FileCoverage.securityChecks`、`Verification.securityReview` 和 `Verification.securityEvidence`；历史报告可以反序列化，无数据库迁移或回填。缺少新契约的新安全检查会显示未完成，不冒充覆盖。

这是一份逐文件专项覆盖清单，尚不是全仓库“入口 × 信任边界 × 子系统”审计图。适用性、检查质量和漏洞语义仍由 Agent 判断；宿主能够核验引用、结构和状态条件，不能证明这些判断正确。没有添加漏洞复现执行器、全仓库深度模式、跨轮根因指纹或自动历史结论复用。

现有每阶段 3 分钟、总计 15 分钟、最多 24 组、冻结上下文和输出预算继续生效。证据引用最多 80 行/项，安全文字字段最多 4000 字节，链最多 8 项，专项引用最多 4 项/条、输入记录最多 300 条；输出仍受既有阶段总预算约束。不自动重试付费模型请求。

## 验证

- Core 审查单元测试：19 项通过，覆盖伪造运行结果、错误原文、同名跨项目、混合版本、超限链、缺失防护、未解条件、独立复核降级、复核补证与旧报告兼容。
- Store 审查集成测试：19 项通过，包括新增的多组专项缺失→原材料重试→覆盖完成→投影重建。
- 前端原有全套 368 项通过；新增安全展示及复核补证后，结果组件专项 10 项通过。类型检查、生产前端构建、Core/Store 严格 Clippy 通过。
- 真实 Kimi 2.1.1 隔离验收：最终运行 `completed`，结构化报告、六类专项、两个独立 Session、两次冻结上下文请求、来源恢复和样例未修改均通过。发现删除文档属主检查的候选问题；由于上游授权/入口等条件仍未知，宿主将 Agent 提议的 `confirmed` 降级为 `uncertain`，同时保持审查流程已完成。这验证了状态约束，不等于漏洞实际复现。
- 首轮真实验收暴露“待核实结论误算为执行失败”和补证缺少独立保存位置，修正后第二轮通过。没有将首次失败记为通过，也没有仅为获得 confirmed 反复调用模型。其他供应商本轮未逐一真实验收。
- 前端及桌面开发构建通过；本轮未重启用户生产后台服务。运行中的旧服务需要重新加载新二进制才会使用新契约。

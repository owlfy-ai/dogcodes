# 远控物理连接迁移基础（2026-10-22）

## 当前交付范围

PC 和手机页面已接入二进制 H.264 管线的租约迁移。初始独立 RTP 连接无法建立而落到 WSS 时，手机会按连接重试间隔在后台建立新的、独立认证的 P2P 候选；已验证直连后才迁移。原中继和画面在准备期间继续可用，不复用主业务连接。二进制 DataChannel 的短期凭据到期前也会建立新候选接续，失败保留健康旧通道并继续重试。

同编码预算的 RTP→RTP 原位迁移与手机续期也已接入。手机先准备独立 peer 和 renderer，PC 原子更换 RTP 输出，按新代次 ready 和 IDR 恢复；SDK 报告实际首帧后才替换旧画面。准备和接管不重新创建采集、编码器或 Controller。

**已支持二进制→二进制、同编码预算 RTP→RTP，以及二进制 H.264 ↔ RTP 的编码器重建接续。跨模式保留租约、共享屏幕授权及输入状态，按目标输出预算重建视频流；原生采集可能重启。更高 RTP codec level 协商、真实 TURN 服务续期、弱网和跨平台实机联调尚待验收。** 本地迁移验证不代表全部远控网络场景完成。

同编码预算的 PC 迁移不会重新创建 Lease、屏幕采集、编码器或输入 Controller，不释放正在按住的按键，也不重置输入序号。二进制输出在已有 RelayVideo 内原子换绑到新连接，旧连接视频代次作废，新连接需要安装解码器/监听并确认 ready，之后从关键帧恢复。原有会话协议适用于经认证的 WSS 和 WebRTC DataChannel；单纯换数据通道不意味着协商了更高的视频 codec level。

## 认证与授权生命周期

- 原生 Connection 携带此次 Noise 握手验证的完整手机公钥。只有当前物理 owner 能发起 offer，候选连接必须是同一公钥的新连接；迁移 ID 本身不足以让另一台已配对手机接管。
- 原有 Wayland 授权使用可切换的所有者活性引用。候选连接 stage 成功后，在最多 20 秒内与旧 owner 共同保持来源有效；claim 后只有新 owner 保持来源。旧连接关闭不会结束已经迁移的共享授权。
- stage 之前旧物理连接断开仍走原有恢复流程。stage 之后旧线路结束可暂时保留采集；若双方断开、准备超时、电脑锁定或 OS 撤销授权，租约/授权按原有规则终止。没有把临时迁移票据作为永久 OS 授权。
- 同一时刻最多一项迁移。票据、owner 和计数器属于 PC 的短期屏幕租约，Core 重启后该租约即结束；不恢复或重放旧键鼠事件。

## RPC 契约

方法：`remote_desktop_handoff`。所有阶段携带 `leaseId`、UUID v4 `ticket` 和 `phase`；手机每次尝试生成新 ID，重试时参数冻结。

| phase | 发起连接 | 参数与行为 |
|---|---|---|
| offer | 当前 owner | `expectedRevision` 字符串，来自 open 的 `handoffRevision` 或视频保活回覆；接受时计数器递增。重复相同请求不延长 20 秒期限 |
| stage | 同一手机的新认证连接 | `videoTransport: binary/webrtc` 在首次 stage 冻结，可与来源不同；二进制携带 `chunkedMessages: true`，RTP 候选必须已有兼容的视频协商。绑定唯一候选，回传当前描述，不向新通道提前发布帧 |
| claim | 已 stage 的候选 | `expectedInputSequence` 字符串，必须等于 PC 最后接受的输入序号；检查通过才换 owner/输出通道，结果为 applied |
| status | 发起连接或候选 | 只核实已有阶段及当前描述，不重新执行 claim；已 applied 的原请求可重复读取 |
| cancel | 发起连接或候选 | 未应用时退休票据；若已应用则返回 applied，不能宣称回滚成功 |

回覆包括 `state`、`leaseId`、`monitorId`、`inputSequence`、`inputBatch`、`revision`、当前物理连接是否拥有租约的 `owner` 布尔值，以及 `video`。已退休/尚不存在的票据可只读返回 retired，但不表示历史上从未受理；只有 revision 已大于原 offer 的 expectedRevision，才证明该冻结 offer 不能在未来受理。offer 还绑定原视频实例和已应用的尺寸版本；准备后切屏或改变编码配置，会拒绝用旧准备结果 claim。

当前 owner 还可先取消尚未受理的 offer：若版本仍相等，取消会先递增版本，阻止晚到的原 offer；重复取消不重复递增。版本号在 offer 被接受时也会递增，取消/到期后仍保留在 Lease。迟到的原 offer 携带旧 expectedRevision，无法复活已经退休的迁移；不需要无限增长的票据墓碑。新的尝试读取新版本、创建新 ID。结果未知的 claim 不能因一次 status 仍为 staged 就当成未执行：旧请求可能还在队列。退回旧通道前必须取得 cancel 栅栏结果；结果仍无法核实时应结束两条远控连接并走原有恢复，不能重放键鼠。

## 手机接入与恢复规则

`RemoteInputQueue.pause()` 暂停启动新批次，只等当前已经发出的批次确认；期间新触摸仍合并/排队。返回 false 表示处置中断、输入结果未知或迁移被取消，禁止 claim；`resume()` 中途取消旧屏障后，迟到回复不会让旧迁移复活。

1. 页面根据 PC open 的 handoff 能力决定是否后台尝试。二进制由 DirectDialer、RTP 由 DesktopDialer 建立新连接，均完成固定 PC 公钥/新 Noise 身份验证；缺能力的旧 PC 保持原流程，不发新方法。首次升级只接纳已确认的 direct，不能把未确认 WebRTC 路径标为 P2P。
2. offer/stage 后预建二进制解码器或 RTP renderer 并绑定候选 stream，再暂停输入、等待在途批次确认并冻结序号。发送闭包在发批次时读取当前路由。主业务连接不参与租约交接，也不会被关闭。
3. 只发送一次 claim。丢失回复后查询原候选的状态，未获应用证明再请求取消栅栏；一次 staged/not-found 不能被当作操作失败。取消获证后恢复旧通道，应用获证后切换新通道，仍未知则结束两条远控连接后恢复，不重播键鼠。
4. owner、输入序号、来源实例/尺寸版本及新代次均核对后，输入可继续走新通道。新监听器安装、ready 与实际首帧完成后（RTP 使用 SDK 的 onFirstFrameRendered，尺寸事件不算首帧），才替换旧纹理并关闭旧物理连接。缩放/平移、修饰键状态和原 Controller 保留。
5. 旧线路在 stage 后结束时，暂停新输入、等待候选结果；若旧在途输入已未知则不能迁移。切屏等待正在提交的交接，准备期间的切屏/退出使旧准备失效。旧线路迟到断开事件按物理连接身份过滤。
6. 二进制及 RTP 管线凭据续期均使用迁移协议，可交接到第三条及后续物理连接。成功后计时器绑定新凭据；失败重试且不强制关闭健康链路。二进制运行时每 10 个保活周期抽样实际路径，区分 P2P、TURN、未确认 WebRTC 与 WSS；抽样失败不结束健康视频。

跨二进制/RTP 模式的编码器重建接续见文末；更高编码能力协商、真实 TURN 凭据服务和弱网/路由变更验收仍开放。RTP 迁移前若旧视频 worker 已经退出，迟到 stage 不能复活它；改走连接恢复。

## 二进制 H.264 ↔ RTP（编码预算重建）

- stage 冻结目标 transport。候选 RTP 必须已协商 CB 3.1，描述返回目标 `profile`（`cb31` / `cb-auto`）及 `switchingCodec`；几何尺寸仍可能是旧值。重复 stage 不允许修改目标，旧视频实例/尺寸版本/输入确认序号的栅栏保持原样。
- claim 保留 Lease、Controller、输入序号和 Resize 实例，切换物理 owner/输出代次。不同预算先标记 `codecReady:false`，输出在编码器确认、客户端 ready、IDR 三项满足前不能发布。视频线程作废旧回调、停止旧 VideoStream 并按目标预算重建，随后更新实际尺寸和 `codecReady:true`；输入/RPC 工作线程不等待原生重建。重建可能重启原生采集；Wayland 复用原 Portal Source/授权。
- 手机先准备候选 renderer/decoder、排空旧输入，再 claim 一次。控制通道接续后最多等待编码器 10 秒，期间只读取冻结租约，核对 transport/profile/实例/尺寸版本/代次。二进制目标按确认的实际几何尺寸创建解码器，不能使用 stage 的旧尺寸。
- 跨类型保留旧 decoder/renderer 的纹理和显示几何。RTP 使用 SDK 实际首帧，二进制等待 native decode 输出；尺寸事件不能提前替换纹理或改变旧画面比例。退出/迟到回调共享资源清理所有权。准备失败可保留旧通道；已 claim 后重建或首帧失败则关闭原租约、回退独立 JPEG 连接，不回滚或重放输入。
- 二进制中继可升级到已验证 P2P 的 RTP；RTP 凭据续期在媒体连接失败时可接续独立二进制中继。主业务连接不承担视频迁移或大视频流。RTP 仍协商 CB 3.1，没有新增更高等级的 SDP 能力；Windows/Linux 的软件后备输出在两种 transport 中仍受 CB 3.1 预算约束。

本地编码管线验收使用隔离 Linux 容器、合成 RGBA ScreenSource 和真实 OpenH264 编解码：同一来源双向重建，未 ready 不发布，新输出从可解码 IDR 开始，最后关闭释放来源。该测试按需启用，不接触实际屏幕。另有真实 SDP sender + 无采集 Lease 的协议测试，以及手机目标 profile 不符时拒绝接管的协议测试、混合模式/实际首帧门槛/超时和退出清理的页面测试；页面的 native 解码/SDK 事件为替身。它们不替代硬件解码器、真实网络和系统权限验收。

该验收还复现并修复软件码率调节问题：OpenH264 的 `SPATIAL_LAYER_ALL` 上限不更新 layer 0 的上限；超过初始码率就可能报错。升码率先提高 layer 0/总上限，降码率先降低目标，再降低两级上限。真实编码器验证了初始 2 Mbit/s → 3 Mbit/s → 100 kbit/s → 9 Mbit/s → 1 Mbit/s → 2 Mbit/s，并读取 native target/fps/layer cap；仍保留原流和协商的 CB 3.1 限制。

# 普通发送意图的后台登记与共享恢复

日期：2026-10-16。对应 DT-09 / DT-10，承接[普通发送恢复](desktop-submission-recovery-2026-10-16.md)。本工作块迁移原发送记录的持有与发现；实际执行继续复用 Core 命令、版本条件及事件。没有新增数据库表、迁移或项目单写锁。

## 持有与协议

`agent-protocol::submission` 与 TypeScript 协议描述完整原意图：原 task/project/版本、目标 Agent、正文和发送选项、附件引用，以及创建/上下文确认/最终提交的固定操作 ID。上下文保留原区间和包哈希。当前可信本机调用使用 LocalUser；配对身份、跨网传输和 Dart 接入仍属后续范围。

daemon 的 `SubmissionIntents` 持有 `submission-intents/<operationId>.json`。Tauri 的单一 `core_submission_intents` 入口转发 Put、Get、List、Resolve、Close。Get/List/Resolve 只读，空查询不创建目录；List 分页返回待处理或不可读记录的身份，单条详情单独读取，无法识别的目录条目由 `unrecognizedEntries` 明确报告。记录按类型化原内容计算 SHA-256，排除界面展示元数据及派生 checkpoint，不允许同 ID 改正文/目标/原版本。同任务或 scope 的不同待处理原请求不能同时登记。

写入先写私有临时文件并同步，再原子发布；Unix 同步记录及父目录。结束时原子替换为紧凑的指纹和结果，不继续在恢复记录中保留重复正文，也不删除规范历史里的原消息。损坏、身份错配、非规范文件身份或符号链接路径拒绝处理。异步调用和阻塞文件操作分别保持串行，避免调用被取消时阻塞写入仍运行却提前释放保护。已有 daemon 实例身份负责宿主服务唯一性。

## 结束的证据

Close 不接受客户端自行声明“成功/取消”。Core 的只读 `pending_command_invalidation_receipt` 核实原命令回执或原作废事件，包括请求指纹、事件边界、task stream、任务、causation、原操作 ID / 类型 / 版本。

创建已受理时从原 `task.created` 推导版本；上下文已确认时从原 `task.preferred_executor_changed` 推导版本，不使用最新 bootstrap 或客户端 checkpoint 替代。只有最终原 SubmitTurn 已受理、且原 `turn.queued` 身份和版本吻合，才能报告 submitted；否则须有原阶段或最终发送的作废证据。查不到回执、仅完成创建/切换、事件不一致，都保留待核实状态。submitted 表示受理，不是 Agent 执行完成。

旧本地记录或并发登记失败的请求，可以凭上述 Core 证据直接结束，不必先占用另一客户端已占有的待处理位置。没有证据的 Close 不写记录。已经结束的原 ID 再 Put 返回原结果，不能复活为待发送状态。

## 桌面接入

原请求先保存在本机缓存；resume 在任何创建、切换或发送之前完成后台 Put。登记响应丢失会保留同一身份，不继续执行，后台已登记记录可被另一入口发现。缓存写入仍失败时安全停止；并未取消离线草稿。

恢复面板挂载、恢复网络、窗口聚焦及每 15 秒共享轮询进行只读发现；后台登记/结束/删除清理现已补即时变更提示，同一个 CoreClient 的多个组件共用订阅与轮询，见[订阅记录](desktop-submission-watch-2026-10-16.md)。清空界面缓存后可重新获得后台原内容。发现记录不会自动导入未登记的旧本地意图，不执行任务；继续或放弃仍由用户选择。新发送准备前先刷新后台待处理记录，后台登记再次仲裁并发竞争。

查询已结束记录时携带本机预期原内容，服务端验证指纹后才清理本地缓存。后台返回的规范化字段顺序/展示元数据不会误判身份；本地已验证的 checkpoint 保留。同步失败显示错误并阻止未经核实的新发送，可手动重新核实。消息已受理而 Close 响应失败时仍保留记录，之后查原消息即可结束，不再次发送。

浏览器 Demo 保留既有内存机制；生产 Tauri 提供登记、查询、分页、证据解析及结束接口，不会静默回退。真实双客户端 RPC 测试覆盖登记响应丢失后的查询与同 ID 重试。

## 永久删除后的普通发送恢复

后续工作块发现：永久删除清除 task 事件，只保留 `task.deleted` 永久标记；创建/发送/作废的旧 Ack 虽仍可能存在，其事件边界已不能再次读取。不能把缺失事件当成未发送，也不能让已删除会话的恢复记录无限保留正文。

现新增独立 `task_deleted` 结果（taskId / deletionSequence）。Core 通过有界任务事件查询核实类型、stream、任务 ID、永久标记和有效事件版本；仅任务投影不存在或 receipt 不存在不算删除证据。该结果只说明原会话已永久删除、不能继续该请求，不断言删除前是否执行。原受理/作废回执不作改写。

`Resolve` 只读解析，旧本地意图也可调用，已有后台身份仍须匹配原指纹。显式核实、继续、放弃先取得后台解析结果，再经 Close 的持久响应清理本地。结束响应失败保留本机记录。旧窗口晚到的 Put 在有永久删除证据时直接保存紧凑结束记录，不登记成新的 pending；Core/SQLite 的删除屏障仍阻止实际继续执行。

daemon 删除路径同步处理对应发送记录，包括将以前的 submitted/invalidated 记录标记为 task_deleted，并清掉待处理记录中的重复正文。另一任务的记录不改动。后台启动时重试清理“数据库删除已提交，但发送记录转换尚未完成”的中断窗口；清理出错记录诊断并保留可核实数据，不伪装清理成功。单个损坏记录的故障隔离及长期目录扫描开销仍需继续改善。

界面明确显示“原会话已永久删除，发送恢复记录已结束。”，不显示“已放弃尚未受理”或“原消息已受理”。App 清理对应乐观占位，避免再读取已删除会话。

本工作块 **70 个前端、22 个原生用例及类型检查通过**：前端普通流程 15、共享恢复 18、恢复界面 5、Tauri 协议 11、实际草稿会话入口 21；原生意图与 daemon 专项 18、既有永久删除生命周期 4。覆盖创建/作废事件被清除、已受理发送随后删除、删除后宿主重建补清理、真实 daemon dispatch 删除、其他任务隔离、旧窗口晚登记、Resolve 不写文件/事件和结束失败时保留缓存。服务重建测试复用真实 SQLite/文件存储，不替代三平台独立进程验收。

## 后续故障隔离

单条损坏记录曾阻断其他记录的发现和删除后清理，现已修复：保留坏记录并显式报告不完整，同时继续独立核实其他记录；界面同时展示错误和可读恢复入口，新发送仍受严格准入限制。专项 75 项前端、20 项原生及类型检查通过，见[故障隔离记录](desktop-submission-isolation-2026-10-16.md)。这补齐上述单条异常问题，长期扫描开销和其他工作流仍待完成。

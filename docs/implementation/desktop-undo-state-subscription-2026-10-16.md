# 逐轮撤销恢复与后台状态订阅

日期：2026-10-16。对应 DT-08/09/10。复用现有撤销备份及文件操作 journal，不重建 Core 事件库。

## 撤销身份与结果

- `core_turn_undo` 和后台 Undo RPC 增加必需 operationId。与暂存/文件修改共用 `MutationOperations`，完整绑定 taskId、artifactId、expectedPayloadSha256 和 confirmed；回复丢失可通过既有 `core_review_file_operation` 查询原操作。
- 后台在同一 ReviewHost gate 内校验任务、处理持久回执并执行撤销。继续由 Core 验证不可变 Artifact 的归属、内容哈希和媒体类型，客户端不传文件字节或恢复路径。
- `ReviewStore::undo_turn` 原有按 task/artifact 保存的撤销清单及逐文件备份仍是事实来源；同一轮已完成撤销不覆盖用户后续编辑。journal 负责调用身份和回复丢失，不替代文件事务，也不自动继续部分撤销。
- `TurnUndoAction` 使用端内持久原请求；结果未知时展示“核实撤销”，隐藏再次确认入口，关窗重开仍保留身份。已知失败也先核对再结束跟踪。收到原成功回执才标已撤销；旧的状态查询回复不能覆盖更新的状态。既有布尔状态接口继续用于显示当前撤销事实。

## 跨进程刷新

- 去掉原仅在发起撤销的桌面进程内发出的 `turn-files-changed` 通知。后台 ReviewHost 在 Git、文件修改和撤销返回后发布状态失效提示（包括返回失败/部分结果的情况）；会话删除也触发提示。
- `review/watch.rs` 提供有界 watch 通道，最多 64 个后台订阅。只保留最新变更提示，不排队存每次操作的历史；真实业务结果仍查持久回执/撤销记录。订阅建立及重连都会要求重新查询，断线期间无需重放提示事件。
- 新增认证本机流 `review_watch`，桌面桥接为 `core_review_watch` / `core_review_unwatch`。15 秒心跳、45 秒客户端读取超时、15 秒写入超时；断连释放订阅许可，窗口销毁取消转发任务。复用已有窗口转发注册表并使用独立 key 命名空间，不让订阅保留后台空闲退出的请求锁。
- `reviewWatch.ts` 按会话在当前 JS 上下文共享一条流，最后一个监听者释放时关闭；重连采用新 ID 和退避，旧连接迟到事件无效。撤销卡片、Git 恢复面板和文件恢复面板收到提示后查询事实源，不自动重发副作用。
- 当前注册表为 104 个入口，其中生产 102 个。通知是提示层，不是另一套业务状态；没有为只读状态查询写持久操作记录。

# 终端关闭的结果恢复

> **已简化（2026-10-23）**：本文的撤回／栅栏协议已移除。停止任务、重命名、删除、关闭终端改为可安全重发：确认时只读回执或实际状态（运行是否结束、名称是否已变、会话是否还在、终端是否已退出），未确认就重发同一操作；「不再等待」只清除手机上的记录。保持唤醒改为直接设置并回读，不再跟踪。`command_retirements` 表、`session_command_receipt`/`retire_session_command`、`power_preferences_operation`、`terminal_stop_operation` 均已删除，数据库格式回到 1。下文保留作历史记录。


适用手机终端页的“关闭当前终端”，以及运行页的停止、重启。电脑端本地终端仍可调用原 `terminal_stop`，两条路径共用 TerminalHost 的实际停止逻辑与受理锁。本文不表示保持唤醒、所有终端输入或其它写操作已完成恢复审计。

## 请求与回执

能力标记 `terminalStopRecovery: true`；网关方法 `terminal_stop_operation`：

```json
{"type":"execute","request":{"operationId":"UUID","terminalId":"UUID","expectedEpoch":"UUID"}}
```

`type` 还接受 `get`（核实）与 `retire`（结束跟踪）。三项身份始终冻结。PC 检查目标终端及当前后台代次；旧后台记录不能触发按旧 PID 停止进程。相同 operationId 的请求内容必须完全相同。没有回执的 get 不代表请求不会稍后到达，只有 retire 的栅栏确认才能结束未受理请求。

PC 在触碰进程前，把受理记录原子保存到终端数据目录 `stop-operations/<operationId>.json`。文件写入同步，Unix 同步目录；存储失败不进入进程停止。回执不重复保存终端命令正文或 PID，只保存原请求、状态、错误与最小终端身份/退出证明。

| 状态 | 含义 |
|---|---|
| stopping | 停止调用已发出，尚未确认进程退出 |
| stopped | 原终端已被观察为 exited，退出证明已保存 |
| unknown | 后台重启或在受理后中断，无法证明原终端结束；不重复执行停止 |
| failed | 停止调用报错，仍需核实实际状态 |
| rejected | 原终端/后台代次不符，未执行停止 |
| retired | 尚未受理的原请求已被持久取消 |

已存在的受理记录始终禁止重新执行同一个停止操作。受理与 OS 进程停止不能构成同一个磁盘事务，因此受理后中断可能得到 unknown；不能把 accepted 当作 stopped，也不能为了拿到成功回执再次发信号。已观察的退出证明先保存再返回，正常终端元数据的异步保存即使晚到，重启后仍可恢复该证明。Failed 的启动记录不冒充退出证明。

## 手机恢复与取消

发送前持久保存原请求、项目与终端名称。首次关闭只轮询原回执等待退出，不重新发送停止；超时、断线和未知结果保留恢复卡片。核实使用 get，用户明确重试时仍使用相同请求。只有 stopped、rejected 或 retired 可自动清理跟踪；stopping、unknown、failed 保留。

用户明确结束跟踪时，先持久保存 `phase: retiring`，再发 retire。取消回复丢失后，重试只继续取消，不重新发 execute。未受理时在同一受理锁下保存栅栏；已经受理的停止无法撤销。结束已有记录的跟踪无需再写入退出检查点，避免存储故障令一个已经有栅栏的请求无法结束跟踪。结束跟踪不表示原进程已退出。

手机检查请求指纹、终端 ID、后台代次、项目及退出状态；错误或迟到回执不能清掉不同的新操作。确认关闭对话框期间连接变化，会要求重新确认。运行页重启必须先获得原终端的 exited 证明，再检查原运行配置仍一致，才启动新进程；待核实的停止不会自动接着启动。

## 本地验证范围

- PC 受理/存储测试：取消与迟到执行竞争、重启保留栅栏、请求复用不符、受理后中断不重发、旧后台代次拒绝、存储故障前不停止进程、结束跟踪不需要新检查点、退出证明先于普通元数据恢复。
- Mac/Linux 使用临时目录与测试自己创建的 PTY/进程；不操作用户终端。网关测试确认能力标记、鉴权入口及退休后的迟到调用拒绝。
- 手机测试覆盖原请求跨应用恢复、缺失回执、取消回复丢失、未知结果、错误身份/退出证明、迟到旧回覆，以及终端关闭/运行重启/确认时换连接的真实页面入口。没有使用真实用户进程。
- 正常 PC Core、模拟器安装与跨平台实机联调维持用户当前安排，未为验证替换日常后台。更新两端后，新能力才可用；旧 PC 明确提示更新，不退回缺少恢复能力的旧关闭调用。

本轮最终验证：Mac PC 完整库 309 项通过 / 7 项 opt-in 跳过；Linux 终端完整模块 23 项、远程工作区模块 13 项通过；Mac/Linux all-targets 严格 Clippy 通过。手机完整普通回归 312 项通过（含身份/加密 FFI），Flutter analyze 无问题；正常入口 iOS 模拟器包与 Android ARM64 调试包构建通过。PC 中包含 6 项关闭故障/存储用例和 1 项网关新增用例；手机新增 7 项恢复用例及 3 项页面用例。另一个终端记录损坏时，已完成关闭的证明与安全取消路径仍能使用。

## 手机独立关闭记录（后续更新）

新关闭请求保存到安全存储 `dogcodes.terminal-stops.v1.<hostId>`，按 operationId 独立保存，目标绑定原终端 ID/epoch。同一原终端未决时不再创建另一个停止身份；不同终端可以分别关闭、核实或结束跟踪，不占用 Git/发送等普通待确认槽。最多保留 64 项，达到上限时在发送前提示核实。

Agent 停止与终端关闭共用按安全存储实例串行的短元数据写入队列；网络调用不占该队列。空闲时释放队列尾 Future，既保护多个 MobileOperations 实例的并发更新，也不把已结束调用的异步环境长期保留。核实/取消只清理完全匹配的原记录，旧回复不能删掉新记录或其它终端。

终端页和运行页在有高度上限的滚动区展示对应项目的关闭卡片及原普通待确认卡片；待处理页展示全部关闭记录并计数。卡片核实/重试显式使用自身冻结记录，不借用当前普通待确认操作。关闭证明只清理对应终端的会话视图。

原记录另保留 commandId/directoryIndex 等来源信息。同一项目/目录/命令的关闭仍待核实时，新的运行启动先只读核实原关闭回执，必须取得 stopped 的实际退出证明才继续；其它目录/运行配置不受影响。原有重启仍要求先退出，再核实运行配置一致，不会自动接着启动。

旧应用已保存到普通槽的关闭记录继续通过原记录核实、取消和重试，不在升级时抛弃未知结果；该旧槽在原记录解决前维持既有规则。新关闭始终进入独立日志。移除电脑会串行擦除普通、Agent 停止和终端关闭记录，损坏的 JSON 不阻止擦除，也不允许晚到的准备阶段继续发送新的关闭请求。

验证：手机完整 354 项通过（含原生身份/加密 FFI），Flutter analyze 无问题；普通 iOS 模拟器/Android ARM64 包构建通过。新增用例覆盖并行终端、跨操作实例更新、普通待确认并存、同一目标重复关闭、旧记录恢复、移除电脑、配置启动的目标隔离和退出证明、小屏多卡片与待处理页。未安装到模拟器或操作用户真实进程。PC 协议没有新增，仍使用已验证的 terminal_stop_operation 和原退出证明。

输入写入的顺序、断线后的未知结果和旧连接部分输入隔离仍未完成；须在 PC 中提供会话/后台代次和单调输入序号及失效栅栏，手机只排队不能作为完成依据。

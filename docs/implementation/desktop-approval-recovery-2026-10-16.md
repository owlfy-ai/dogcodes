# 审批与回答的持久恢复界面

日期：2026-10-16。对应 DT-09，接续[审批来源与回执基础](desktop-approval-receipts-2026-10-16.md)。本工作块接通主会话审批/回答的固定操作身份、只读恢复、显式修改未受理决定及后台状态刷新。普通消息发送、新建会话等其他入口仍需继续，不能据此标记全部操作可靠性或桌面发布完成。

## 发送与恢复

`approvalOperations.ts` 在第一次发送前冻结 taskId、原版本、原 turnId/approvalId/请求事件序号、回答和固定 operationId。通过后台准备接口取得规范指纹，然后成功保存恢复记录才发送；准备或本机存储失败时不发送。持久记录只包含白名单查询信息、原版本、时间及是否已确认受理，不保存回答正文、选项、表单或会话标题。完整输入仅保留在当前调用/界面内存中。

每个操作使用独立存储键。同一来源的操作借助本端队列和可用时的 Web Locks 协调；没有 Web Locks 的不同窗口也不会覆盖对方的查询身份，真正受理仍由后台版本条件和固定请求指纹裁决。若同一审批存在多条未核实记录，先分别核实，不擅自选择其中一条继续。

`ApprovalRecovery.tsx` 独立于审批卡片和输入框展示；挂载、重开及收到任务版本更新时只查询回执，不发送决定。复用现有任务投影的版本，不建立第二套事件订阅；后台投递变化与较早查询竞争时补一次只读查询。结果为已投递时结束本机跟踪；已受理但投递未知/失败时保留说明并禁止再次投递。用户可显式结束已受理请求的跟踪，此操作不撤回决定，也不表示任务完成。

未找到回执时不假定失败：用户在原卡片重新选择/输入，先查询原回执，再用原版本、来源和 ID 计算指纹；只有原选择/回答一致才发送原请求。已确认受理后即使查询临时缺失，也不能再次发送。旧查询只处理原操作记录，不删除其他窗口或后续操作的记录；切换会话/客户端后旧回调不更新新界面。

如果只读查询先未找到回执，再观察到任务版本高于原版本，随后再次查询仍无回执，则原版本已不能通过事务条件，可以解除本机跟踪并请用户重新确认。不会在同一次提交中自动换版本、换身份重发。

## 修改尚未受理的决定

仅靠上述机制，若原回答被校验拒绝而任务版本没变，会阻止用户改正答案。新增显式 `invalidate_approval_response` / `core_invalidate_approval_response`，由“修改未受理的决定”按钮调用；挂载、刷新及普通回执查询不会调用它。

后台先核实原回执。已受理则返回原回执，不撤回；未受理时读取当前任务版本，用该版本条件写入 `approval.response_invalidated`。写入后的任务版本使此前快照中的原回复不能再被受理。这里使用后台观察到的当前版本，不能只拿调用者传入的较低版本作为证明。记录不包含答案，不调用驱动、不批准/拒绝请求、不取消任务。它只作废原版本的未受理回复，原待审批请求仍由原投影维护。

作废与审批受理共用 SQLite 的版本条件：若原审批抢先受理，返回原回执；其他并发状态变更导致条件冲突且没有回执时，要求再次核实。作废使用派生的固定幂等键，并绑定完整查询信息和原版本；回包丢失后重试读取原作废回执，不再增加任务版本，因而不会把后续新决定再作废。后台重开后同样有效，无数据库迁移。任务流版本的变更可能使其他并发写入遇到版本冲突，各入口按自身恢复流程处理，不自动重放副作用。

前端收到已作废结果才解除原跟踪，刷新任务并让用户重新确认；若原决定已受理则继续查询其投递。出现网络错误或无法核实的结果保留原记录。

审批卡片 React 身份包含原轮次和请求事件序号：同一原生审批 ID 被复用时重新建立表单。失败期间保留当前界面的输入，重开窗口不恢复回答正文。恢复成功只清理对应审批的错误，不覆盖其他操作的错误。

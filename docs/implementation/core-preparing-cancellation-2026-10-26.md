## 修复的问题

会话创建/恢复、上下文准备和附件校验可能发生在原生 prompt 之前。此前，取消虽已记录 `turn.cancel_requested`，投递任务仍会立即查找原生句柄并 interrupt；句柄未取得或 Driver 尚未进入可取消状态时，投递失败，准备流程却继续发送 prompt。另一处风险是取消已接受但异步投递尚未开始时，准备流程越过派发边界。

现在每个自有 Run 固定持有一个运行控制对象，与 Driver、实际 SessionHandle 一同绑定原运行：

- 取消命令先经过原有版本/运行校验及持久化。只有非重复的已提交取消，才设置停止标记；在发布接受事件和调度取消投递之前设置。过期或被拒绝的命令不影响运行，重复命令不重复投递。
- 准备开始和派发准入都检查原运行停止标记。停止接受与派发准入在同一 watch 状态锁内排序，不持锁等待原生请求。准入前停止则不调用 Driver.prompt。
- 准备期间已经发出的 new/load 等调用仍由原流程等到结果，不丢弃其未来。返回的原句柄会显式关闭，包括支持会话常驻复用的 Driver；关闭确认前任务仍在停止中。清理失败保留实际失败，不伪造已确认中止。
- 已进入派发准入但 Driver.prompt 尚未返回时，取消等待原调用的就绪或结束状态，不提前投递一个必然无法找到活动轮次的取消，也不重新发送 prompt。取得事件流后，用原 Driver/原句柄投递 interrupt。
- 没有派发的任务沿用现有 `turn.failed / failureKind=interrupted` 表达中止，附 `nativeDispatched=false`；不会写 `history.native_prompt_accepted` 或伪造 `turn.interrupt_sent`。待发送上下文没有因此被标为已送达。
- 取消已接受后，迟到的附件再校验错误不覆盖停止结果；未取消的任务继续严格执行原完整性检查。
- 已开始的自主续轮直接进入运行阶段，仍使用原句柄。正常原工作结束会唤醒等待取消的任务；工作未来被放弃时明确标记 abandoned，释放等待但不把它当作原生完成证明。所有权释放后移除控制对象，不绑定后续同名会话。

状态对象只描述本 Core 对原运行的准入/投递阶段。`finished` 表示本地结果处理结束，不能证明一个结果未知的原生请求、子任务或进程已经退出；原有 Driver 回执和物理退出证明仍需保留。

## 验证

新增八项真实 SqliteStore + Core 命令路径回归。Driver 是私有内存夹具，没有启动已安装 Agent 或模型：

1. 创建会话尚未返回时接受取消；迟到的原句柄获证清理，prompt/interrupt 均未发送。
2. prompt 调用尚未就绪时取消，重复同一命令不会另建投递；就绪后仅 interrupt 一次。
3. 版本过期的取消被拒后，原准备和 prompt 正常完成。
4. 原关闭故意阻塞时保持停止状态；另一个任务能够独立完成，原关闭确认后才记录中止。
5. 派发本身失败时，等待取消得以结束，不伪造原生取消已发送。
6. 等待工作区访问、尚未创建会话的任务被取消后，既不创建原生会话，也不发送 prompt。
7. 原关闭报错时，不把未知清理报告为已确认中止，夹具中的原资源仍由原 Driver 持有。
8. 等待创建期间取消，再改变附件文件；停止仍生效，不把迟到再校验错误当成这次运行结果。

另新增一项 Core 生命周期回归：派发等待中的取消，在原 RunOwnership 被丢弃后被 abandoned 唤醒，不声称原生完成，也不留下控制对象。上一轮原句柄传递测试改为明确模拟已就绪的原生工作，继续验证取消/审批/问答使用原 scope。

## 后续范围

本轮没有中断、重新派发或猜测一个尚未返回的原生请求。若某 Driver 的 prompt 准备本身长期不返回，取消会保留原等待，而不是靠一个 Core 超时伪造结束；需继续核对各 Driver 的就绪与原生终止预算。异常中止的工作者也仍需原资源清理及恢复核实，不能从控制对象被移除推断物理进程结束。

原生派发后记账失败的清理、失败设置的原生资源、其他 Driver 的 scope、未标识回调及 Core 强退/重启继续处理。视频实机恢复和其它功能/网络/部署范围仍按 CURRENT_WORK 的八包计划推进。

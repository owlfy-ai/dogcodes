# Cursor CLI 升级锁排查与修复（2026-09-25）

## 复现与原因

用户看到的通用提示是“更新命令未成功（退出码 1）”。用当前安装的原生更新命令及 dogcodes 同样的受限环境复现，实际错误是 `Another CLI update is already in progress`，对应 `~/.local/share/cursor-agent/.install.lock`。

检查时锁文件为空，没有进程持有它，也未发现对应安装目录的升级进程。Cursor 2026.09.18 的本地更新器会自行清理超过 60 秒的锁。等待其过期后，官方更新器正常下载安装并移除锁，没有手动删除锁或结束用户进程。

另一个明确存在的触发风险是额度查询：dogcodes 为读取 `/usage` 启动短时 Cursor TUI，而旧版 Cursor 默认在启动约两秒后尝试后台更新。额度读取完后退出，后台下载可能尚未完成，容易留下锁或与用户手动升级冲突。无法追溯历史锁的精确创建者，不能将本次锁的来源断言为某一次额度查询。

## 修复

- 额度 TUI 加 `--disable-auto-update`，确保读取额度不会启动后台安装器。
- 桌面 ACP 探测/注册由可信适配器加入相同选项；驱动会话切换权限时保留此选项并防止重复添加。
- 保持 manifest 的非 flag 参数限制；没有放宽不可信清单可以提供的命令选项。
- 原生升级锁错误改成具体中文提示，仍不把任意命令输出、账户信息或锁路径发给前端。不强制移除可能正在使用的锁。

## 本机验证

- 官方原生更新器从 2026.09.18-9a7762b 升级至 **2026.09.23-86fc751**，退出 0，约 65 秒。稳定启动链接及 `--version` 均指向新版。
- `about` 确认当前版本和最新版本一致，`latestStatus = up_to_date`。
- 旧版（仍有更新可用）和新版分别运行修复后的真实 `/usage` 读取，均通过；未发起模型对话，验证后没有升级锁残留。
- ACP 单元测试 32 项、更新模块测试 17 项、ACP manifest 测试 1 项通过；桌面构建和 Rust 格式检查通过。
- 运行中的 dogcodes 已加载当前构建；重新扫描 Cursor 返回 `ready`、无诊断错误，版本记录为标准化后的 `2026.9.23-86fc751`，原生显示为 `2026.09.23-86fc751`。

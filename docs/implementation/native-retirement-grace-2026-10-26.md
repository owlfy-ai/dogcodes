# 原生配额退役等待与快速重建

日期：2026-10-26。接续 [采集隔离](macos-capture-isolation-2026-10-25.md)。本轮修改共享 `video/worker.rs`，不修改手机/服务端协议，也不增加原生线程上限。

## 已复现的竞态

当一个原生上下文已经挂住，另一个健康上下文正在结束时，两个名额暂时都占用。旧 `Permit::take` 立即返回繁忙；即使健康上下文马上归还名额，切换分辨率/profile 或重新连接仍失败。

新增回归在生产逻辑修改前失败，见 `/tmp/dogcodes-slot-grace-before.log`：实际获取路径报告池满之后才释放正在退出的上下文，替代实例仍得到错误。测试不通过 sleep 猜测是否已经达到池满状态。

## 实现

- 采集与 codec 仍各限两个名额。每个池增加独立的 availability 锁和归还通知；原生上下文真正析构后，Permit 在同一锁下归还名额并唤醒等待者，避免检查与休眠之间丢失通知。
- 池满时最多等待两秒，且不能超过本次初始化预算。两秒来自现有单次原生运行期限，不是延长每个请求的无限重试。一直未退出的上下文仍占名额，第三个初始化不会开始。
- 初始化使用一个绝对单调时钟期限，从申请配额前开始；等待名额、创建线程、等待就绪共用这个期限。名额归还后不会重新获得完整的五秒/十秒初始化窗口。
- 新原生线程执行初始化前再次检查原 owner 和期限，完成后也核实期限；已过期的任务不通过迟到 ready 变成成功。运行请求自己的期限保持不变。
- 等待不持有 native 对象的锁，也不在配额锁内执行创建/析构/用户回调；原生析构不能被强杀，本轮没有假装释放仍挂住的上下文。

继续参考本机 RustDesk HEAD `53996e3c4`，其 `src/server/video_service.rs` 的 `DxgiRecoveryState` 区分有限恢复与后备，并使用有边界的时间窗口。本项目采用相同的有界恢复原则，独立设计名额通知与初始化预算；没有复制 DXGI 实现或把其重试次数直接套用到线程配额。

## 验证

新增四条跨平台 worker 回归和一条 macOS 实际 VideoToolbox 回归：

- 一个上下文挂住、另一个正在退出时，codec/capture 均能等待归还并成功替代，初始化期间计数始终不超过二。
- 名额永久占用时，短预算在原预算内失败，长预算也只等待两秒宽限；初始化副作用计数保持零。
- 初始化预算一秒，其中 600ms 已用于等退役名额；新初始化继续阻塞时，外层按原期限返回，而不是再等一秒。
- 每个池在保留一个模拟挂住上下文时，完成 24 次有握手的连续重建；观察信号按申请线程 ID 区分，不会误用上一次或其它申请者的池满通知。
- 同样保留一个模拟挂住 codec 的情况下，实际 VideoToolbox 连续创建/编码/销毁八次；每次得到当前输入时间的可独立解码 IDR，并验证深/浅画面不是上一实例的旧图。这里只用合成 NV12，没有采集实际屏幕。

在独立源码副本中，分别取消配额等待、移除归还通知、恢复“配额之后重新计算整段超时”，对应测试均失败。继续使用上一轮修正后的私有 target：每次清理原生包、确认旧测试产物消失，再编译指定副本并记录路径/源摘要，不共用 live target 的反例产物。反例之后再清理、编译当前工作区执行完整验证。
